# 奶粉公开投诉分拣：关键词规则 vs AI 的一个小型概念验证

> **性质声明。** 这是作者个人的概念验证作品，与任何奶粉品牌及其合作方无关：未与企业接触、未访谈、未上线。样本是黑猫投诉公开列表上某奶粉品牌一个产品系列的 41 条投诉（投诉原文为公开数据，原样保留，其中会出现品牌名）（2026-07-15 至 10-15）。仓库里的一切数字都只描述这 41 条样本，**不是准确率，也不能外推到总体**（原因见第三节「怎么读这张表」）。

在线演示（静态页，不调用模型）：<https://martin-cell-blip.github.io/feihe-complaint-triage/>
代码仓库：<https://github.com/Martin-cell-blip/public-complaint-triage>（演示页的 URL 路径沿用首次发布时的目录名，内容已去品牌名）

## 一、场景

消费者服务专员每周把公开投诉平台上的新增投诉分给三方：质量部门（奶粉本身的问题）、活动运营（集罐、买赠、积分等规则与兑现）、电商运营（拒发、订单异常）。难点有两个：

- 一条投诉常混着几个问题，不同的人分法不同；
- 写到食用后症状的信号可能跟着活动类投诉流走，进不了质量核查。

AI 在这里只负责一步：读一条投诉，给出类别（五选一）、一段≤40 字的逐字原文依据、是否写到症状、是否需要人工复核。不自动回复，不判断责任与异物成分，不给任何喂养或医疗建议。提示词全文在 [`src/prompt_classifier.txt`](src/prompt_classifier.txt)（当时实际使用的提示词原样保留，其中写有品牌与系列名，因为投诉原文就是这样写的）。

## 二、流程四步

| 步骤 | 做什么 | 脚本 / 文件 |
|---|---|---|
| 1 采集与脱敏 | 黑猫投诉该品牌商家页公开列表（未登录）→ 筛选标题或摘要含该系列两个产品名之一 → 脱敏成公开版 | `src/00_anonymize.py` → `data/public/` |
| 2 清洗与查询 | 去重、派生字段（提及渠道、是否截断、是否提到症状、批次号）→ SQLite → 三组 SQL | `src/01_prepare.py`、`src/03_run_sql.py`、`src/analysis.sql` |
| 3 两种方法分拣 | 关键词规则（含只调换顺序的 v2）与 Claude 离线批量分类，同一批文本、同一套类别 | `src/02_baseline_rules.py`、`labels/claude_labels.json` |
| 4 对比与测算 | 与参考标签逐条对照 → 演示页 → Excel 测算 → Word 案例 | `src/04_evaluate.py`、`05`、`06`、`08` |

**关于 AI 结果怎么来的。** `labels/claude_labels.json` 由一个不读参考标签的 Claude 子代理在 2026-10-15 离线一次性生成；仓库里的脚本**不调用任何模型**，复核参考标签后也不重新生成预测。演示页里的分类与依据就是这份文件；页面上粘贴的新文本只走页面内的关键词规则，一律标为「需人工复核」。

## 三、规则基线 vs AI：原始读数

以下直接取自 [`outputs/eval_cases.csv`](outputs/eval_cases.csv) 与 [`outputs/eval_summary.json`](outputs/eval_summary.json)（`python src/04_evaluate.py` 生成）。

| 方法 | 类别与参考标签一致 | 质量安全漏判 | 质量安全误判 | 需复核标记与参考一致 | 依据 |
|---|---|---|---|---|---|
| 关键词规则 | 35/41 | 0 | 2（17400228971、17401788734） | 38/41 | 只有命中的关键词 |
| 规则 v2（只调换顺序） | 37/41 | 0 | 2 | 38/41 | 同上 |
| AI（Claude） | 41/41 | 0 | 0 | 40/41 | 41/41 条依据可在原文逐字找到 |

**怎么读这张表（照抄 `eval_summary.json` 的「说明」字段）：**

> 一致率用来定位错误类型：参考标签由作者借助 Claude 标注、尚待人工复核，与 AI 同源，AI 的一致率会偏高；41 条样本适合找出错误模式，不足以估计总体准确率。

复核状态同样来自该文件：`"复核状态": "参考标签待人工复核"`，`"已人工复核条数": "0/41"`。因此表里的 41/41 **不是** AI 的准确率，只说明 AI 与一份同源标签没有分歧；真正能从这张表得出的结论是下面几条。

**规则错在哪（可在 `eval_cases.csv` 逐条核对）：**

- 5 条订单发货中有 4 条被规则分进活动权益，因为「活动」「补贴」「积分」等词先命中。例如「淘宝百亿补贴……超时不发货」命中了「补贴」。
- 赠品滑板车「踏板内部异物凸起」命中「异物」，被当成奶粉质量问题（17401788734）。
- 把订单规则调到活动规则前面（v2）修好 2 条，又把「承诺的赠品不发货」「拒发赠品」错分成订单（17401080047、17400293346）。词义重叠靠排顺序解决不了。

**AI 的增量与边界：**

- 增量：词义重叠时的语义区分（规则任一版本分错、AI 分对的有 6 条），以及每条都能几秒钟核对的逐字原文依据和复核理由。
- 边界：规则在质量安全上 0 漏判，高风险分流不需要 AI；设计取舍是规则做高风险兜底（命中质量或症状词就强制复核），AI 负责其余条目的分拣与摘录依据。
- 难判断的例子：17400228971 同时写了活动、发货和「孩子吃了拉肚子」，AI 归为活动权益但标出症状并要求复核；17402080517 AI 比参考标签多标了一次复核，偏保守。

**样本结构（SQL，`outputs/sql_*.csv`）：** 质量安全 18 条、活动权益 18 条、订单发货 5 条；「异物/虫」在 15 条独立投诉中出现；活动权益 18 条里 13 条属于「规则没讲清或系统限制」（集罐不累计、扫码手机号限制、空罐丢失锁权益等），5 条是「承诺未兑现」。占比以 41 条公开投诉为分母，只描述样本结构。

## 四、成本测算与盈亏平衡

公式与默认假设在 [`src/common.py`](src/common.py)，Excel「成本测算」表里黄色格为同一组假设、可改，绿色格为公式。

净价值（元/周）＝ 每周条数 ×（每条可节省 − 模型费）− 维护成本

| 假设项 | 取值 | 说明 |
|---|---|---|
| 人工每条分拣＋摘依据＋填表 | 4 分钟 | 假设，试点时用秒表实测替换 |
| 工具辅助后每条复核 | 1.5 分钟 | 假设 |
| 质量安全类占比 | 18/41 | 实测；这类仍须人工通读，不计节省 |
| 人力成本 | 60 元/小时 | 假设 |
| 模型费用 | 0.01 元/条 | 假设上限 |
| 维护与抽检 | 2 小时/月 | 假设 |

| 每周新增条数 | 净价值（元/周） | 情形 |
|---|---|---|
| 3.2 | −23.3 | 本系列公开投诉（实测：41 条 / 13 周） |
| 11.4 | −11.8 | 该商家页全部品牌公开投诉（实测：160 条 / 14 周） |
| 约 20 | 0 | 盈亏平衡点 |
| 50 | +41.9 | 假设：再加一个电商平台的差评 |
| 200 | +250.8 | 假设：多平台差评加客服工单 |

结论：按现在的公开投诉量，单独做不划算，关键词规则加一个 Excel 模板就够了；只有扩展到电商差评或工单、每周量超过约 20 条时，才值得作为现有智能体平台上的附加能力试点。测算只计效率收益，结案提速、同类投诉减少等经营收益未计入。

## 五、试点继续 / 停止标准（4 周试点）

- **继续**：守住零漏标（质量安全与写到症状的条目，以人工复核为准），改类率不超过 10%，实测每条耗时下降，且周量达到盈亏平衡或有明确的扩展计划。
- **停止**：出现规则也没兜住的症状或质量漏标；改类率超过 20%；或者周量长期低于盈亏平衡、也没有扩展计划。停止后退回「规则 + Excel 模板」。

主要成功指标是「一次派对率」：当周新增公开投诉中，专员复核时没有改类、并且附有原文依据的条目占比。

## 六、数据与脱敏

- **来源**：黑猫投诉 · 某奶粉品牌商家页「最新投诉」公开列表，未登录只读，2026-10-15 采集，列表滚动加载到 2026-07-09 共 160 条，筛出 41 条。单条详情页不登录打不开，所以只用列表摘要（30 条被平台截断）。
- **保存了什么**：投诉单号（公开页面 URL 里的编号）、日期、回复状态、标题、摘要、投诉对象、诉求。**没有**保存昵称、头像、用户 ID。
- **脱敏**：`src/00_anonymize.py` 把原始件转成 `data/public/heimao_complaints_20261015_public.json`：字段白名单；文本里平台已打码的订单号、运单号、手机号片段（7 处，涉及 4 条）替换为「［编号已隐去］」；未打码的手机号和 12 位以上纯数字也会被替换（本样本没有）。替换明细在 `data/public/anonymization_report.json`，`python src/00_anonymize.py --check` 可在没有原始件时复查公开版。
- **不在仓库里的**：原始采集件 `data/raw/`、喂给模型的 `data/ai_input.jsonl`（与脱敏前的 `text` 列相同）、港交所年度业绩公告 PDF（见 Excel「来源」表链接）、开发过程截图。
- 投诉单号保留是为了逐条核验原文链接；这些链接指向公开页面。

## 七、复现步骤

环境：Python 3.10+，`pip install openpyxl`；生成 Word 需要 pandoc 与 `~/.claude/tools/md2office/ref_portrait.docx`（没有可改 `src/08_build_docx.py` 的 `REF_DOC`）；重拍截图另需 Playwright（可不装）。

```bash
python src/01_prepare.py          # 公开版 JSON → data/complaints.csv、data/case.db
python src/02_baseline_rules.py   # 关键词规则基线（含 v2）→ labels/baseline*.json
python src/03_run_sql.py          # src/analysis.sql → outputs/sql_*.csv
python src/04_evaluate.py         # 对照参考标签 → outputs/eval_cases.csv、eval_summary.json
python src/05_build_demo.py       # → demo/投诉分拣演示.html（双击打开）
python src/06_build_excel.py      # → docs/奶粉投诉分拣案例_数据与测算.xlsx
python src/08_build_docx.py       # → docs/奶粉公开投诉分拣_AI小场景案例.docx（公开版）
```

持有原始件时在最前面加 `python src/00_anonymize.py`。参考标签人工复核用 `python src/07_review_sheet.py make | apply`，回写后从 03 起重跑；详见 [`运行说明.txt`](运行说明.txt)。
